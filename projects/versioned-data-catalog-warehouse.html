Versioned Data Catalog Warehouse

Analysts could only query the data catalog one asset at a time, with no history. I turned it into a warehouse they can analyze with plain SQL.

  • Python
  • DuckDB
  • Parquet
  • SCD Type 2
  • REST API

The Problem

The enterprise data catalog could only be queried through its API, one asset at a time. Analytical questions (“every field of every message stream, with its business terms and downstream tables”) needed thousands of calls. There was also no history, so nobody could see what changed between exports.

What I Built

An ETL pipeline that loads periodic catalog exports into a single DuckDB file of a few GB:

  1. Schema from Parquet: base tables created directly from the export.
  2. Incremental SCD Type 2 load: every record carries _is_current and effective-from/to dates, so history is preserved across snapshots.
  3. Curated views: one flattened view per asset type (stream fields, API fields, DB columns, screens, files, data quality rules), with the generic asset/attribute/relation joins already resolved.
  4. Validation and benchmarking: automated tests after every load.

Why This Approach

DuckDB gives warehouse-style analytics in one file, with no server to run. Flattened views keep every consumer from writing its own fragile many-way joins. Views are defined in exactly one script, which refuses to rebuild if the database contains a view it doesn’t own. That stops hand-made views from silently disappearing.

Outcomes

  • Millions of records queryable in milliseconds to seconds.
  • Became the single catalog source for the web explorer, the lineage skills and the reporting.
  • Some views were rewritten for speed. For example, a lean mapping view runs about 15x faster than the generic one, and list-typed columns removed a cross-product fan-out.

Lessons

Treat analytical views as code: one owner, tests, and a check that refuses to drift.
